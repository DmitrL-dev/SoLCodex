# Nested-tool edit gate development probe — 2026-09-24

The [action-fusion pair](2026-09-24-action-fusion-mechanism-development.md) did not execute the intended mechanism. ON put a here-document edit and verifier in one shell command; the edit failed and the verifier still ran. This follow-up checks whether the *current Codex tool surface* can sequence a patch tool and a verifier tool within one programmatic outer call. It is a host-contract probe, not another repair pair or a token-saving measurement.

## Observed local probe

In one `functions.exec` invocation, the program awaited `tools.apply_patch` to create a scratch file containing `duration=2\n`, checked for a tool error, then awaited a distinct `tools.exec_command` verifier. The patch call resolved with an empty object; the verifier checked the exact file bytes and exited `0` with `verified`. In a second invocation, the patch expected a nonexistent old line. `tools.apply_patch` threw `apply_patch verification failed`; the program exited before calling `tools.exec_command`. A separate read confirmed the original bytes remained and the verifier's sentinel file did not exist.

These two observations demonstrate sequential nested calls and a fail-closed branch for the *observed thrown patch error*. They do not prove that every failed patch has the same response shape: an empty success object gives no portable explicit status field. They also do not attest independent approvals. This task uses an approval policy of `never`, so no file-change or command approval decisions were emitted or tested. The pilot CLI may expose a different tool surface; no model chose the nested calls in this probe.

The [OpenAI programmatic-tool guide](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling) permits nested `apply_patch` and shell tools, but advises direct calls by default for writes or approval-sensitive actions and requires each call's permissions and errors to be checked. The [Codex app-server contract](https://learn.chatgpt.com/docs/app-server#approvals) distinguishes `fileChange` and `commandExecution` approval requests and final item states. Those are capability and protocol descriptions, not evidence that this local `never`-approval probe exercised both decisions.

## Gate before an efficiency experiment

The next frozen development test needs a target CLI inventory of nested tools and their success, error, and decline response shapes. A deterministic dispatcher test must then cover successful patch → verifier, failed or declined patch → no verifier, accepted patch with declined verifier, nonzero verifier status, and cancellation between calls. With approvals enabled, capture separate approval decisions and item IDs. A live model smoke can use an explicitly specified nested-tool pattern on the already exposed duration fixture to test adherence; it cannot be pooled with the earlier pair or called independent repair evidence.

Only after the tool and adherence gates pass should fresh independent repair tasks compare quality and all-attempt usage. Evidence must link the model response to one outer program and two ordered nested calls, show no intermediate model inference, preserve both statuses in the next request, and account for provider usage. Until then, separately calling the patch and verifier is the safe fallback. The [skill source](../../plugins/sol-codex/skills/efficient-agent-loop/SKILL.md) and session-start guidance now forbid shell edit-plus-test bundling; this source change does not attest that an already installed plugin has refreshed.
