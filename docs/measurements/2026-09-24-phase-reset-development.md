# Diagnosis-to-edit phase reset: one exposed development task (2026-09-24)

An external orchestrator ran one diagnosis-only session on the already-exposed [packaging #928](https://github.com/pypa/packaging/issues/928) fixture. The diagnosis left the parent tree unchanged and ended with a 114-word handoff. The **reset** arm got a fresh Codex session, the same tree, and that handoff. The **resume** arm continued the diagnosis session with its full conversation. Session IDs confirmed that reset was new and resume reused the diagnosis session. Both were asked to implement the same repair. This is a separate host-level hypothesis; the SoL Codex installed plugin and receipt adapter were disabled.

The [aggregate JSON](data/2026-09-24-phase-reset-packaging-dev.json) gives fixed fields, trace and patch hashes, the parent Git tree ID, and the frozen design hash; private traces, authentication, worktrees, and patches are withheld. Both arms used `codex-cli 0.155.0-alpha.16.3`, `gpt-6-luna` at low effort, the same parent fixture and external checker, separate Codex homes, a local model-host allowlist proxy, and macOS Seatbelt. The reset home was copied after diagnosis and still contained the prior session files; a distinct new session ID does not prove those files were inaccessible. The private verifier was denied to the agent by a read probe. This is development containment, not the Linux worker isolation required by the confirmation draft. Reset ran first, with no randomized order or replicate.

The parent scored 8/14 and the historical fix 14/14 on the external matrix. The upstream pass counts differ because each agent added its own passing tests; both complete suites exited zero. The 583 deterministic generated expression cases were designed **after** the run and compared each agent patch with the historical fix. They include nested valid and malformed forms but do not prove complete preservation. Both patches passed `git diff --check` after application to separate clean parent copies.

The reset arm used 47,169 fewer CLI-reported input/output tokens (−20.0%) including the **same** 59,893-token diagnosis cost in both arms, and took 7.304 seconds longer (+10.23%). It made eight edit-phase tool calls versus five after resume. Cached input fell from 199,168 to 148,480, while uncached input rose from 33,888 to 37,839. These are one task's completed-turn CLI counters, not a provider request ledger or bill. The arms took different trajectories and produced different patches. No causal or general savings estimate follows.

For a hypothetical three-category price schedule with uncached-input, cached-input, and output prices `u`, `c`, and `o` per token, the **observed CLI-category** reset-minus-resume difference is `3,951u − 50,688c − 432o`. Reset is cheaper under that model only if this expression is negative. These prices and the relevant billing semantics have not been established for the ChatGPT-authenticated route; the inequality is a sensitivity check, not a money-saving result.

The first private evaluator falsely marked both repairs unaccepted: it ran `git diff --check` in a copy without a `.git` directory, even though the behavior checker printed 14/14. After inspecting this failure, the evaluator was corrected to initialize and commit the parent copy before applying each **already-saved** patch. No model run was repeated. The [public corrected evaluator](../../scripts/evaluate_development_patch.py) and its [synthetic regression test](../../scripts/test_evaluate_development_patch.py) reproduce that procedure. It reapplied both saved tracked patches to clean parent copies and recorded apply success, `git diff --check` exit 0, and external verifier exit 0 with 14/14. Neither agent left untracked files. The private correction record and public evaluator code hashes are in the aggregate. The runner code itself was not hash-frozen before execution, and this tracked-patch evaluator does not handle the complete file snapshot required for confirmation. These facts keep this pilot exploratory. A future phase-reset test needs frozen runner code, randomized order, multiple independent tasks and seeds, blinded external checks, and complete request accounting.
