# Correction: SymPy neighboring-class checks establish a behavior change, not a proven regression

Earlier development reports called the shared `_ArrayExpr._iterable = False` repair a quality failure because two post-hoc checks failed. That conclusion was too strong. The checks show that `ZeroArray` and `OneArray` change classification under `sympy.utilities.iterables.iterable` and `is_sequence`, and that `flatten([array])` stops returning the dimensions. We have not established that preserving this behavior is a required SymPy API contract. The [natural-history aggregate](data/2026-09-24-sympy-dev.json) now has schema version 2, null adjudicated acceptance for both arms, and a SHA-256 link to its prior version. Its observed run scores and token counts are unchanged.

| Source | `iterable(ZeroArray(2,3))` / `is_sequence` | `list(ZeroArray(2,3))` | `list(ZeroArray(3))` | `flatten([ZeroArray(2,3)])` |
| --- | --- | --- | --- | --- |
| Parent and historical fix | `True` / `True` | `[]` | `ValueError` | `[2,3]` |
| Shared-superclass repair | `False` / `False` | `[]` | `ValueError` | `[ZeroArray(2,3)]` |

The same matrix holds for `OneArray`. It was rerun in separate isolated imports of the pinned parent, historical fix, and clean agent-patch replay on macOS arm64 / Python 3.12.13. The `_iterable` flag affects SymPy's predicates and `flatten`, not direct Python iteration or `as_explicit()` in these checks. The [historical `iterable` documentation and implementation](https://github.com/sympy/sympy/blob/530149cc7256a98c5963bcccc43cec19a9d04d09/sympy/utilities/iterables.py#L3025) describe `True` as permitting finite `list(...)` traversal and explicitly allow `_iterable = False` when recursive traversal is undesirable. The parent says `True` for a symbolic array whose actual list traversal is empty or raises, depending on shape. `flatten` returns dimensions because it descends through the [symbolic object's arguments](https://github.com/sympy/sympy/blob/530149cc7256a98c5963bcccc43cec19a9d04d09/sympy/tensor/array/expressions/array_expressions.py#L133), not because it extracts array elements. We found no historical test or documented promise that `flatten` must expose those dimensions.

There is also a plausible architectural case for the broader flag: the historical [`MatrixExpr` superclass](https://github.com/sympy/sympy/blob/530149cc7256a98c5963bcccc43cec19a9d04d09/sympy/matrices/expressions/matexpr.py#L58) sets `_iterable = False` and tells genuinely iterable subclasses to override it. The [original issue](https://github.com/sympy/sympy/issues/26807) identifies false iterable classification as the cause of recursion. The [merged PR](https://github.com/sympy/sympy/pull/26809) changed only `ArraySymbol`; that establishes the historical patch's scope, not a prohibition on changing sibling classes. A maintainer explicitly noted limited familiarity with these objects during review. The analogous matrix design is evidence for plausibility, not proof that every `_ArrayExpr` subclass should be atomic.

**Corrected decision:** the original frozen verifier remains 35/35 for both repairs, the 48 selected upstream tests still pass, and the later v2 remains 35/37. C19/C20 are valid compatibility-change detectors but unqualified acceptance requirements. The repairs' external acceptance is **unresolved**, not zero and not one. The observed ON total of 418,639 versus OFF 613,638 CLI-reported tokens is neither a quality-adjusted saving nor a proven quality failure; request-level provider billing is also incomplete. Treating parent-and-gold agreement as sufficient to define the specification would have falsely made a plausible broader fix a mutation kill.

The [source-level probe](2026-09-24-sympy-verifier-known-miss-development.md), [six-variant diagnostic pilot](2026-09-24-sympy-diagnostic-mutants-development.md), and [two later repair attempts](2026-09-24-sympy-blind-repairs-development.md) retain their measured scores and hashes. Their labels are corrected: the superclass edit and its M5/M6 sibling ablations have disputed quality status, so they do not count as established wrong fixes for a six-mutant qualification. Future verifiers need an independently justified requirement or adjudication for each preservation control before it can reject an agent repair. This issue remains exposed development material and provides no held-out SoL efficiency estimate.
