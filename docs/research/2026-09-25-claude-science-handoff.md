# Research handoff: proving SoL Codex efficiency without quality loss

**Status as of 2026-09-25.** This document is a self-contained research brief for Claude Science or another independent scientific reviewer. The public repository is [DmitrL-dev/SoLCodex](https://github.com/DmitrL-dev/SoLCodex), with the evidence described here frozen at commit [`cdc14a471e533a7cb3ab725106cd9407d3d05c82`](https://github.com/DmitrL-dev/SoLCodex/tree/cdc14a471e533a7cb3ab725106cd9407d3d05c82). This brief does not authorize model runs, amend preregistered decisions, or claim a general saving.

## The question

Can a specified SoL Codex intervention causally lower **full provider input-plus-output tokens per independently accepted software repair**, while preserving repair quality within a justified, preregistered margin and without an unacceptable increase in elapsed time? If the answer is yes, which intervention and population does the evidence actually cover? If the installed plugin cannot be measured or cannot replace model-visible tool output at the current host boundary, state that explicitly.

Three interventions must remain distinct:

1. **Installed SoL Codex plugin.** Its `PostToolUse` hook archives large output and emits a bounded receipt. On the tested Codex host, the original result remained model-visible in direct and code-mode probes despite non-blocking feedback. Local `saved_bytes` is not provider-token, billing, latency, or quality telemetry. Direct plugin savings require a separate randomized plugin ON/OFF study and a demonstrated replacement boundary.
2. **Opt-in explicit receipt adapter with bounded artifact search.** This captures output before tool return. It is separate research code, outside the installed plugin. Its extra instructions, invocation failures, retrievals, and fallbacks belong to the treatment.
3. **Quiet-first pytest diagnostics.** This changes the first diagnostic command from verbose to quiet output. It is neither the plugin nor the receipt adapter. A result for this intervention cannot be transferred to either of the other two.

Other ideas, including phase resets and context masking, are separate hypotheses. Do not pool their outcomes with the three interventions above.

## The immediate qualification gap

The v4 control plan contains **19** prospective scenarios. Only a partial `quality_fail_continues` case is recorded. The remaining 18 include full 16-slot completion; incomplete accounting; uncertain cleanup, checkpoint, first-command adherence, or quality report; missing/malformed final evidence; pre- and postflight pin drift; crashes after durable start, after a real CLI/provider request, after seal, and after finish; tampered seal or corrupt journal; accounted early timeout; and lock contention.

Qualification needs fresh invocations of the actual coordinator with pinned CLI and Code Mode host, a local synthetic provider, real broker/bridge and SQLite ledgers, host-owned evaluation, and an independent raw-evidence verifier. Crash tests need an **external supervisor** that observes PID and request delivery, acknowledges the intended fault boundary, kills the process, proves descendants and late requests have ceased, and observes restart behavior. Editing a JSON receipt or polling for a file is insufficient. A started slot must never be retried; incomplete or uncertain usage must never be silently accepted; a terminal failure must identify all unstarted slots.

The published compact four-slot archive does not contain copied CLI binaries, the virtual environment, CLI home, or live workspace. Its verifier does not rerun the evaluator and cannot independently prove actual network delivery, process exit, historical push timing, request-to-attempt identity, or durable crash-boundary acknowledgements. It must remain a **partial recorded-evidence** decision. Four false acceptances found by Astra—protected-test edits, failed isolation canary, empty pytest lifecycle, and terminal `turn.failed`—were repaired and given regression tests before publication; this is not evidence that no other adversarial gap exists.

## Full telemetry: the hard measurement problem

`turn.completed` usage can omit startup work and can disappear after interruption. A local OTel collector can lose buffered data on `SIGKILL`. A CONNECT count proves a connection, not token usage. Provider work may finish after CLI disconnect. Retries and canceled attempts may still incur cost. Therefore neither local CLI traces nor synthetic-provider totals are sufficient for a real economy claim.

Specify a durable **provider-side or externally observed request ledger**, outside the CLI process and inaccessible to the candidate agent, with per-attempt identity, dispatch, provider acceptance, retries, cancellation, completion, final usage, and eventual reconciliation. Reconcile it by attempt ID to CLI trace, delivery ledger, upstream ledger, broker, bridge, and terminal campaign result. Define when an attempt is known complete, a supported lower bound, or unknown. Unknown is never zero. If an unknown ON attempt has no defensible finite upper bound, do not assert a saving. A money claim additionally requires a matching provider bill or a verified provider/model/date price schedule; cache-read, cache-write, uncached input, output, and reasoning categories need their real accounting semantics. Cached input is a subset of input, not an additional token count.

The proposed primary token outcome for arm `a` is:

`K_a = sum(provider input + output tokens across every assigned attempt, including failures and timeouts) / number of independently accepted repairs in arm a`.

Define `R = K_ON / K_OFF`. A zero accepted-repair denominator makes `R` undefined. Keep all four paired acceptance outcomes, wall time per accepted repair, order strata, cache categories, adapter adherence, and infra failures separate. Use ON upper and OFF lower cost bounds when telemetry is incomplete; if those cannot support the decision, report **inconclusive** rather than dropping runs.

## Quality and sample-selection problems

Existing upstream tests alone are not an adequate acceptance oracle. A candidate parent must fail an independently specified defect witness; the historical fix must pass; preservation checks must catch plausible wrong repairs, including changes to tests, disabled checks, nearby symbols, nested scopes, adjacent versions, reruns, and partial-state recovery as applicable. Score the agent checkpoint in a host-owned clean copy, with test files and hidden oracle beyond candidate control. Freeze test inventory and no-network isolation. Distinguish `frozen_test_pass`, `adjudicated_acceptance`, known regressions, unknown quality, and post-hoc check results. Blind reviewers to arm, token count, timing, and run order. Apply any justified post-hoc check symmetrically to parent, historical fix, OFF, and ON. A post-hoc check may inform adjudication but cannot retroactively turn a failed frozen gate into a pass.

Development-exposed defects and related repository lineages must not enter held-out confirmation. The proposed narrow Python quiet screen selects 24 different lineages, eight each for API, build, and state. Its deterministic selector exists, but ancestry-map and sample approvals are pending, so no real 24-task sample has been selected. The broader confirmation draft targets 360 paired tasks, 120 per family, at most one task per independently reviewed lineage. That is a **planning target**, not an achieved or guaranteed-powered sample. Public benchmark tasks can be held out from this project while still having appeared in model training.

Before assignment, independently review the complete required ranked prefix, exclude exposed forks/continuations, freeze exact task IDs and environments, verify parent/fix behavior, and qualify wrong-fix controls. For the 24-task quiet screen the current proposal demands six independently reviewed, non-equivalent plausible wrong fixes per task. The 360-pair draft implies 720 model runs, at least 2,160 wrong-fix constructions, and at least 2,880 parent/fix/mutant verifier evaluations. The estimated 120–360 worker-hours are planning estimates, not observed spend. Claude Science should assess whether a defensible smaller or staged design achieves the decision precision **without** post-outcome task selection or weaker quality checks.

## Causal and statistical design constraints

Randomize assignments before either arm. Run OFF and ON sequentially in isolated workspace, HOME, temp, and local-cache states; balance OFF→ON and ON→OFF within short blocks and task families. Provider-side cache may still carry over. If it cannot be controlled, explicitly define the estimand for that sequential cache regime and report order-specific effects. A run without intended ON adapter invocation is part of the assignment-based effect but does not identify compression's mechanism; report adherence separately. Do not discard such runs from the primary estimate.

Use exposed development tasks with completely accounted repeated runs to calibrate same-task variance and simulate interval precision. Repetitions of one task are correlated and do not increase the number of independent repository lineages. Never increase the confirmatory sample after inspecting an interim effect.

The **draft**, not yet frozen, suggests a point estimate `R <= 0.85`, an upper 95% ratio bound below `1`, a lower paired 95% acceptance-difference bound above `-0.05`, no known accepted-patch regression, an upper full-time-per-accepted ratio no higher than `1.25`, and passed isolation/verifier/adherence/accounting gates for a claim of **some** token saving. A claim of **at least 15%** saving needs the ratio interval's upper bound below `0.85`. These thresholds require independent power/precision scrutiny. A five-percentage-point noninferiority margin supports only “noninferior within five percentage points,” not literal proof of zero quality loss. Any finite sample leaves residual uncertainty about rare harm.

## Requested Claude Science deliverables

1. **Identifiability map.** For installed plugin, explicit adapter, and quiet-first diagnostic separately specify treatment, mechanism, randomized unit, control, causal estimand, eligible population, assumptions, observed boundary, and permitted conclusion. Determine whether the current non-blocking hook can cause or establish reduced model-visible input. If not, specify the minimal Codex host/API capability and a falsifiable boundary test.
2. **Independent accounting design.** Provide a concrete state machine and schema for durable provider attempts, including late completion, retry, cancellation, startup usage, `SIGKILL`, missing usage, and reconciliation to CLI/broker/bridge/SQLite. Derive valid lower/upper cost bounds and precise stop/inconclusive rules. Distinguish token and dollar claims.
3. **Pre-outcome statistical simulation.** Model paired success, heavy-tailed costs, within-task variance, cache/order effects, repository clustering, rare regressions, and zero-success draws. Estimate the independent-lineage sample size needed for the quality and economy intervals. Test whether 24 and 360 are useful at their intended stages. Give predeclared interval, sensitivity, and stop rules without favorable-result sample expansion.
4. **Task and oracle qualification.** Design a feasible ancestry/exposure review, blind curation, parent/fix tests, plausible wrong fixes, alternative valid fixes, independent adjudication, and post-hoc check policy. Estimate workload and propose rigor-preserving efficiencies. Do not select tasks by expected output size or likely treatment success.
5. **Adversarial v4 audit.** Map all 19 planned controls to observable raw artifacts and enumerate uncovered failure boundaries. For each gap, provide a minimal counterexample, independent observation needed, and acceptance test. Distinguish what the current compact archive proves from what needs an external supervisor/full raw tree. Do not treat hash consistency as proof of the event that allegedly produced the hash.
6. **Stage gates.** Provide an ordered GO/NO-GO plan before the next synthetic case, before 16 exposed calibration model runs, before the 24-task quiet screen, and before a new 360-pair confirmation. Each gate must name exact artifacts, an independent verifier, a rejection condition, and the narrow claim allowed after passing. Identify the cheapest decisive experiment likely to falsify the approach early.
7. **Feasibility verdict.** Separate mathematical limits of finite-sample “no quality loss,” engineering work that can be qualified, limits imposed by the current Codex host boundary or provider billing access, impractical resource demands, and hypotheses already weakened by negative development evidence. If general installed-plugin savings cannot be established under current conditions, say so and propose the smallest product or hypothesis change that makes the claim testable.

Do not turn the four synthetic slots or four failed-gate real-model runs into a positive A/B. Do not revise a frozen criterion after seeing outcomes, substitute unknown usage with zero, drop costly failures, count repeats of one defect as independent tasks, or transfer results from another agent/product/paper to Codex without direct testing. Treat the current public Git state and its linked artifacts as evidence; challenge its assumptions and calculations rather than accepting their labels.
