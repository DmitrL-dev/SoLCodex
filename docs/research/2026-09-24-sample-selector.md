## Frozen rule

The target is 120 tasks in each of `state`, `build`, and `api`, at most one task per reviewed repository lineage. The causal estimate is for this selected 360-task mixture under the frozen runner; it is not an unbiased estimate for every SWE-rebench task or repository. Lineage rank is computed before task rank. A lineage with more tasks can be more likely to have an eligible task, but does not receive an earlier lineage rank because of task count.

The curator coordinator follows lineage rank order, including exposed lineages in the rank sequence. Exposed lineages are recorded and skipped; they need no task review. For every other visited lineage, **all** its candidate tasks must have final adjudicated classifications before the selector considers that lineage. The two curators independently assess issue eligibility and all applicable families, with candidate rank hashes, remaining quotas, agent outcomes, and arm assignments hidden. The coordinator may send shuffled batches but must not omit a higher-ranked lineage. Disagreements require a documented resolution before manifest approval. Review entries must form a contiguous prefix of the eligible lineages, with every task ID exactly once. No unresolved or partial lineage is accepted.

For each reviewed task, `eligible_families` is a list drawn from `state`, `build`, `api`. A task with no eligible family has exactly one `exclusion_reason`: `not_repair`, `unsupported_language`, `license`, `image_unavailable`, `fix_leakage`, `unverifiable`, or `outside_families`. Eligible tasks have a null reason. The selector validates exact fields and IDs, rejects extra payloads, and publishes only aggregate reason counts; the reviewed IDs and selected IDs remain private until the once-only analysis. Qualification must reflect runnable images and usable verifiers, not just issue labels.

The selector processes the reviewed prefix in lineage-rank order. It adds each eligible lineage to a three-family capacity matching. Family search order is `state`, `build`, `api`; when a family is full, it tries to move the latest-ranked incumbent to another eligible family first. It keeps a **maximum-cardinality** matching for each prefix and stops at the first prefix where every family has 120 matched lineages. The final assigned task within each lineage is the lowest task hash eligible for that lineage's assigned family. The code is deterministic: small synthetic graphs compare matching cardinality against exhaustive enumeration, while a separate fixture fixes exact assignments and the first stopping point. It validates unique repository and task identities across the entire ranking, strict metadata types, and exposure flags before selection. If the approved review prefix stops early, extends beyond the first feasible prefix, or never reaches all quotas, selection fails. No seed, priority, or quota may be changed after seeing this result.

If a proposed task fails final pre-run license, image, or verifier qualification, its review classification must be corrected with a reason and evidence **before either arm runs**. Reapprove the changed private review hash and replay the same frozen selector from the beginning, extending the reviewed rank prefix if needed. Log every revision and publish aggregate exclusion reasons. A replay can reassign several lineages; simply taking the next task is invalid. Freeze the final 360 IDs, verifiers, code, and hashes before the first arm. No substitution follows the first arm.

[`scripts/select_confirm_sample.py`](../../scripts/select_confirm_sample.py) writes a private no-replace manifest and prints only aggregate counts. Its excluded-lineage count covers the rank prefix **before stopping**, not the entire pool. Even a successful sample output explicitly marks verifier, isolation, and provider-accounting qualification as false and does **not** authorize confirmation runs. The independent [campaign gates](2026-09-24-confirmation-campaign-draft.md) remain required.

An adversarial code review during development found that the initial selector trusted a stale map-approval flag, checked task identity only within each lineage, and lacked a test for exact incumbent tie-breaking. These defects were corrected before publishing a sample. The tests now cover revoked or changed map approval, duplicate and malformed metadata across lineages, exact family/task replay, exhaustive small-graph matching cardinality, and a 360-task synthetic CLI run. That synthetic run is not evidence that any real candidate, curator review, or campaign gate has qualified.
