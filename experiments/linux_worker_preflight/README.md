# Secret-free Linux containment preflight

This development probe tests a small part of the [confirmation worker design](../../docs/research/2026-09-24-confirmation-campaign-draft.md). It runs on a disposable GitHub-hosted Ubuntu VM, uses synthetic canaries and a mock HTTP broker, and makes **zero model requests**. The [workflow](../../.github/workflows/linux-worker-preflight.yml) runs on a controlled `main` push affecting this directory or by manual dispatch. It does not run on pull requests, persists no checkout credentials, and passes no Actions token or Docker socket to the agent container.

The controller pulls `python:3.12-slim` and records the resolved digest before using that digest for every container in the probe. It creates an internal bridge with `gateway_mode_ipv4=isolated` and a separate egress bridge. The agent has only the internal network; the mock broker is connected to both. The broker must reach the egress sidecar and a live host HTTP endpoint on the egress bridge address. The agent must reach the broker while failing direct connections to those same sidecar and host IPs. Public IPv4/IPv6 connection failures are recorded separately as unqualified observations because this probe has no positive control for those external endpoints. Docker's ordinary `--internal` bridge [can still reach host services through the bridge address](https://docs.docker.com/reference/cli/docker/network/create/#network-internal-mode---internal); [isolated gateway mode removes that address](https://docs.docker.com/engine/network/port-publishing/#gateway-modes). These tests cover the recorded topology, not all possible routes or container escapes.

The agent container runs as a non-root user with a read-only root filesystem, no capabilities or privilege escalation, standard Docker seccomp, no published ports, and limits of 2 CPUs, 2 GiB RAM with no extra swap, 64 processes, and a 64 MiB temporary filesystem. Its only bind mounts are a writable synthetic workspace and the read-only probe script. Gold, sibling, host, and fake-credential canaries are readable on the VM but absent from its mount namespace. A symlink and `/proc/1/root` control check for alternate reads. A second run deliberately binds a gold canary into the workspace; the probe must reject that run. The controller inspects actual container settings and cleans up containers and networks before reporting success. Docker documents the [read-only filesystem and bind-mount behavior](https://docs.docker.com/reference/cli/docker/container/run/#mount-volume-read-only---read-only) and [no-new-privileges option](https://docs.docker.com/reference/cli/docker/container/run/#security-opt).

Run on a Linux x86-64 host with Docker Engine 28 or later:

```sh
python3 -m unittest experiments.linux_worker_preflight.test_run -v
python3 experiments/linux_worker_preflight/run.py --output /tmp/sol-linux-containment.json
```

The controller emits a path-free JSON result with its code hashes, image digest, host CPU/RAM, Docker/kernel versions, individual checks, and resource limits. Any missing or false check, unsupported isolated network mode, failed negative control, or incomplete cleanup makes the run fail. The workflow does not upload or commit the result; an independently inspected sanitized aggregate can be published after the first run.

Passing this probe will **not** qualify the planned 4-vCPU/16-GiB, 60-minute, 128-request worker. It does not run untrusted repair code, a real credential broker, the external evaluator, interrupted-request accounting, storage exhaustion, or a full worker lifecycle. The image tag is resolved and recorded at runtime but is not preregistered for a confirmation campaign. Candidate selection and independent review approvals remain pending.
